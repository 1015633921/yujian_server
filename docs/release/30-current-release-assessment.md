# 当前发布能力评估

评估日期：2026-07-12。评估基线为 P1-D 实施前的仓库状态，结论为 **NO-GO**。

## 实施前流程

1. 开发机通过 PowerShell 打包当前源码。
2. 使用代码内默认的服务器和私钥路径通过 SCP 上传压缩包。
3. 在服务器原目录覆盖解压。
4. 服务器现场执行 `docker compose build` 和 `up -d`。
5. 只轮询 `/health`，不执行 migration、readiness、冒烟、观察或自动回滚。

小程序通过脚本改写 `config/env.js`，但测试和生产配置同时保存彼此的 URL。Python 与 Node 只有范围依赖或没有 lock；Docker 基础镜像和 MySQL 使用可漂移 tag。仓库没有 CI、版本号、镜像摘要、部署记录和流量切换机制。

## 六个关键回答

1. **一次发布如何完成：** 人工打包、覆盖、现场构建、重启；步骤不可复现，也不能证明构建内容对应哪个 commit。
2. **发布失败怎么办：** 依赖人工修复或再次覆盖，没有上一镜像和自动切流记录。
3. **数据库失败怎么办：** 迁移未纳入部署流程；虽有备份脚本，但没有 checksum、隔离恢复验收和操作者记录。
4. **应用失败怎么办：** 只能再次 SSH 处理，旧容器已被替换。
5. **如何知道成功：** 只有基础 health；登录、报告、海报、DIY、订单关闭状态和日志指标均未形成门禁。
6. **何时回滚：** 没有量化条件、观察窗口和可执行 Runbook。
