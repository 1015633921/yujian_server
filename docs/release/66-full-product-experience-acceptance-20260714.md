### 6.1 商品与材料数据审计

测试材料接口共返回 423 条材料，后台按 SKU 规格统计 2687 条。只读抽查与脚本审计结果：

- 材料图片 URL 缺失：0 条，但后台 SKU 图片覆盖仍显示大量未完善项，需要区分材料主图与 SKU 规格图。
- `size <= 0`：36 条，主要为新增合金配饰。
- `shape` 缺失：62 条。
- 前台对不规则配饰显示“规格待补”。
- 大量价格仍为 ¥0.01/¥0.02 测试值。

因此材料“能加载”不等于“可正式销售”。上线前需形成一次可签字的数据冻结清单，至少包含 SKU ID、商品名、形状、长宽厚、孔径、单价、库存、上下架、主图和 CDN 可用性。

### 6.2 库存口径

后台仓库库存当前只有一个仓储物料记录、库存 9；商品 SKU 页面却存在数百库存。后台文案说明两者不自动关联。若结算直接扣商品库存，而履约依赖仓库库存，则会出现“系统可售但仓库无货”。

在 checkout 开启前必须明确唯一可售库存来源，或建立可靠的同步与对账机制，并补齐以下能力：

- 下单预占使用哪套库存。
- 取消、超时、退款和支付确认如何回写。
- 仓库盘点差异如何处理。
- 同步失败如何告警和人工修复。

### 6.3 运营数据一致性

后台存在三类高风险测试数据：

1. 两个订单复用同一顺丰运单号。
2. 物流签收发生在订单创建之前。
3. 多份不同时间、不同输入的测算记录关联到同一订单。

正式数据虽然可以在发布前清理，但还需要通过约束或服务端规则防止问题再次发生。仅清空测试数据不能证明根因已经修复。

### 7.3 后台响应安全头

后台 HTML 已包含禁止缓存和资产版本头，但本次响应未发现以下常用安全头：

- `Content-Security-Policy`，特别是 `frame-ancestors`。
- `X-Frame-Options`。
- `Strict-Transport-Security`。
- `Referrer-Policy`。
- `X-Content-Type-Options`。

测试 API CORS 当前返回 `Access-Control-Allow-Origin: *`。结合 Token 认证不必直接判定为漏洞，但正式环境应按实际管理后台和小程序调用模型收敛来源，并补充点击劫持与内容嗅探防护。

管理员列表中存在启用的通用 `admin` 账号。发布前应确认它使用唯一强密码、无默认凭据且确有保留必要，否则应停用。
